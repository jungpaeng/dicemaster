# PRD #4 후속: 첫 표시 초기화와 화면 비율 기본값

2026-10-19 KST. alpha.4의 DLL·기본 cfg를 교체해도 첫 창이 작고 도구의 기본값 복구 후 커진다는 보고를 조사했다.
이번 기록은 초기화 경로와 새 화면 비율 기본값을 다루는 로컬 후보다. prerelease 게시와 이슈 #4 완료는 수행하지 않는다.
에이전트는 게임을 설치하거나 실행하지 않았다. 실제 Windows 결과는 유지보수자의 확인을 기다린다.

## 확인한 원인 경로와 한계

기존 `DicePlugin.Awake`는 설정을 초기화한 직후 렌더러를 생성했다. 렌더러는 기본 배치로 판단한 값을
당시 `Screen.width/height`에 맞춰 계산·제한하고 즉시 저장했다. 이후 `Draw`는 저장한 창을 화면 안으로
제한할 뿐, 화면이 커졌다는 이유로 기본 크기를 다시 계산하지 않았다. 도구 복구는 누른 시점의 화면을 사용했다.
따라서 초기 화면이 작거나 0인 경우 기본 cfg까지 작은 값으로 바꿔 저장할 수 있는 코드 경로를 확인했다.
사용자 환경의 실제 초기 `Screen` 값과 당시 적용된 설정 경로는 확인하지 못했으므로 개별 발생 원인으로 단정하지 않는다.

`ConfigManager.RegisterConfigElement`가 바인딩 직후 로드값을 내부 값으로 복사하지 않는 점도 확인했다. 다만 기존 `Init`은
모든 바인딩 후 `LoadConfig`로 실제 엔트리 값을 동기화하고 렌더러를 생성하므로, 이 사실만으로 cfg 무시를 확정할 수 없다.
수신 BepInEx의 정적 분석에서도 미등록 설정은 orphan으로 보관하며 `Bind`가 읽고 `Save`가 함께 보존한다.
기존 UI 검사는 설정 대역을 사용했으므로 실제 초기 바인딩·로드와 부팅 중 해상도 변화까지 검증한 결과가 아니었다.

## 이번 초기화 변경

- `ConfigManager`는 초기 해상도와 독립적인 기본 씨앗 값 `(20, 20, 1152, 756, 20)`을 등록한다.
- 렌더러 생성자는 설정을 보관하며 창 크기·위치·글자를 변형하거나 저장하지 않는다.
- 처음 표시할 때 너비·높이가 모두 양수인 화면에서 설정을 다시 읽고 기본값 판별·화면 보정·저장을 수행한다.
- 렌더러는 첫 표시 전이나 유효하지 않은 화면에서 계산·보정한 배치로 설정을 덮어쓰지 않고 도구의 위치·크기 변경도 막는다.
- 첫 표시와 도구 기본값 복구는 같은 기본 배치 계산을 사용한다. 사용자 지정 배치는 기존 픽셀 값을 사용한다.

양수인 화면 크기가 모든 환경에서 최종 게임 해상도임을 증명한 것은 아니다. 실제 초기화 순서·화면 전환은 Windows 확인 대상이다.
첫 표시 이후의 해상도 변경마다 비율을 다시 계산하지는 않는다. 저장된 배치는 기존처럼 물리 픽셀 값이며 도구 복구로 현재 화면의 기본값을 적용한다.

## 화면 비율 기본값

새 기본 창은 화면 **너비의 약 60%, 높이의 약 70%**다. 화면 안에서 최소 540×440으로 보정하며,
화면 자체가 그보다 작으면 화면 크기를 상한으로 사용한다. 위치와 크기는 기존 픽셀 설정에 저장한다.
본문 기본 20px에 화면 높이 배율 `clamp(화면 높이 / 1080, 0.85, 4)`을 적용하고 12~64px로 제한한다.

| 화면 | 새 기본 창 크기 | 기본 본문 |
| --- | --- | --- |
| 1920×1080 | 1152×756 | 20px |
| 2560×1440 | 1536×1008 | 27px |
| 3840×2160 | 2304×1512 | 40px |
| 3440×1440 | 2064×1008 | 27px |

이전 750×750/14, 1200×860/20, 1280×960/20 등의 원래 기본 배치와 현재 화면에서 계산한
이전 1200×860·1280×960 배율 기본 배치는 새 기본값으로 이행한다. 위치·크기·글자 전체가 일치해야 한다.
좌표·크기의 허용 오차는 0.01픽셀 미만이며 설정 직렬화의 소수점 왕복 오차만 허용한다.
사용자가 조절한 픽셀 배치와 글자 크기는 유지한다. 이미 540×440처럼 축소된 값이 저장됐다면
자동 축소 결과와 사용자 지정을 구분할 근거가 없어 유지한다. 새 기본 cfg 또는 도구 기본값 복구로 새 배치를 적용한다.

## 적용·설정 동기화·복구

1. 게임을 종료하고 현재 DLL과 `BepInEx/config/DiceMaster.cfg`를 백업한다.
2. 후보 DLL을 `BepInEx/plugins/DiceMaster/DiceMaster.dll`에 적용한다.
3. 기존 설정을 유지하려면 아래 **다섯 배치 키만** 동기화하거나, 실행 후 도구의 기본값 복구를 사용한다.
4. 새 기본 cfg 전체를 적용할 수도 있다. 이 경우 열기 키·주사위 등 다른 사용자 설정도 바뀔 수 있으므로 먼저 백업한다.
5. 문제 시 게임 종료 후 백업 DLL을 복원한다. 변경된 배치까지 되돌리려면 백업 cfg도 복원한다. 세이브 형식은 바꾸지 않는다.

```ini
[DiceMaster]
LogWindowX = 20
LogWindowY = 20
LogWindowWidth = 1152
LogWindowHeight = 756
LogFontSize = 20
```

위 항목은 기존 `[DiceMaster]` 섹션의 값을 수정한다. 같은 키를 중복 추가하지 않는다. 기본 씨앗 값은 첫 표시에서 현재 화면에 맞춰진다.

생성자에 조기 초기화를 다시 넣은 격리 복사본은 새 검사에서 예상대로 실패했다.
[회귀 거부 영수증](../artifacts/issue-4/viewport-defaults-evidence/startup-mutation-result.json)에 기록했으며 생산 소스는 바꾸지 않았다.
기존 공개 alpha.4 DLL도 새 생성자 경계 검사에서 거부됐다. 151개 빌드 입력과 읽기 전용 참조는 빌드 전후 같았고,
ZIP CRC·정확히 cfg와 새 DLL 두 파일·각 바이트·해시를 검증했다. 게임 DLL·소스는 포함하지 않았다.
독립 검토에서도 현재 입력·해시·패키지와 실제 DLL의 지연 초기화·저장 보호·고정 창 호출을 확인했다. [최종 검증 영수증](../artifacts/issue-4/viewport-defaults-evidence/local-verification.json)에 기록했다.
설정 쓰기 횟수·화면 변화·Unity 배치는 명시적인 관리 대역이며 실제 BepInEx 디스크·Unity/native 실행 결과는 아니다.

```powershell
Get-FileHash .\DiceMaster-source-candidate.zip -Algorithm SHA256
Get-FileHash .\plugins\DiceMaster\DiceMaster.dll -Algorithm SHA256
```

새 후보는 유지보수자의 Windows 확인 전까지 미완료이며, 원격 게시·버전·일정은 별도로 결정한다.
