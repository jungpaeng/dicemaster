## 실제 자료에서 발견한 수정

- 루트 전체의 선택지 발견 예산과 각 선택지의 누적 후속 분석 예산을 분리한다. 같은 이전 접두부를 choose마다 다시 읽던 경로를 사전 경계·테이블 세대·대입 이력으로 바꾼다.
- 안쪽 인덱스 주석 때문에 바깥 선택지의 `if`가 잘리던 경계를 고친다. 다음 같은 깊이 인덱스·형제 분기·다음 사용자 선택의 경계는 유지한다.
- 이름이 같은 안쪽 함수·지역변수·반복문 변수와 다른 객체의 속성을 바깥 choose에 결합하지 않는다. 재대입은 이전 결과를 무효화한다. 전체 Lua 바인딩·upvalue 실행을 추론하는 구현은 아니다.
- 선택지 본문을 추출하며 제거된 복합 조건·미증명 바깥 조건·choose 이후 분기 이전의 공통 실행 구간은 구조화한 불확실성으로 남긴다. 효과를 `가능한 변화`로 표시하고 읽기 복구 후에도 현재값 예상으로 승격하지 않는다. 조건 원문을 표시·진단하지 않는다.
- 긴 본문은 유한 추적 예산 안의 완결된 접두 효과를 보존한다. 잘린 호출·분기를 평탄화하거나 한도 밖 효과를 가져오지 않는다.
- 원본 IL에서 같은 등록 경로임을 확인한 `SetCurrentStoryScript`를 `SetNextScript`와 함께 추적한다. `SetEnableActions`는 정수 1일 때만 `이야기 조작 허용`, 나머지는 `이야기 조작 차단`으로 표시한다. [API 근거와 연출 경계](ISSUE-2-API-SEMANTICS.md)를 따른다.

실제 자료에서 resolve한 choose→결과 분기 사이 998개 구간은 모두 `menudialogs.<dialog>.SetActive` 호출이었다. 파서 경계 오인은 아니지만 이 UI 상태 변경의 콜백·게임 상태 변화가 없다는 증거는 확보하지 않았다. 따라서 현재 corpus의 선택지 3,530개 모두를 보수적으로 가능성으로 표시한다. 기존 미증명 marker 1,548개에 공통 실행 구간의 영향을 받는 marker 1,503개·choose 전용 479개가 더해진다. 효과 수치 자체를 임의로 바꾸지 않으며, 이 문맥에서는 현재 상태를 실행 시점 상태로 가정한 center·mental 예상량을 만들지 않는다. 공백·주석·세미콜론만 있는 순수 합성 선택지는 확정성 증명을 유지한다.

## 후속 추적 구조와 지원 경계

후속을 재귀적으로 끝까지 따라가던 처리를 FIFO 작업 큐로 바꾼다. 현재 선택지 본문을 먼저 분석하고 가까운 연결부터 처리한다. 각 작업은 진입 경로·깊이·스크립트 종료 시 manager 바인딩 상태를 가진다. 같은 대상이라도 두 manager의 유효성 조합이 다르면 별도 문맥으로 분석하고, 같은 문맥의 합류는 중복 확장하지 않는다. 경로 안의 순환과 서로 다른 경로의 합류를 구분한다. 예약 시점 뒤의 재바인딩도 후속에 반영하며 한 형제 경로의 재바인딩을 다른 형제에게 전파하지 않는다.

고유 스크립트 수는 루트 포함 32개다. 두 manager의 4가지 상태에 따라 실제 확장 문맥과 입장한 작업은 최대 128개로 제한한다. 읽기 실패가 고유 스크립트 계수에 들지 않아도 대기열이 무한히 늘어나지 않는다. 한도는 알려진 효과를 지우지 않고 Partial/Unsupported와 이유를 남긴다. 예약은 실행 보장이 아니며 후속은 계속 `이후 가능한 변화`로 표시한다. 최종 예약 덮어쓰기·빈 값·동적 값·return·다음 choose 경계는 유지한다.

`PreviewParseCache`는 파서 인스턴스가 소유하는 정확한 본문 키의 LRU다. 기본 상한은 64항목·UTF-16 1,048,576자·262,144토큰이며 하나의 큰 항목은 다른 항목을 비우지 않고 캐시를 우회한다. 토큰만 재사용하고 효과·조건 결과·현재 능력치·읽기 성공/실패는 재사용하지 않는다. 선택지와 이벤트 정의는 각자의 소유 파서 안에서 공유 후속 토큰을 재사용한다. 정상 표시 갱신은 기존 고정 분석을 사용한다. `ClearCaches`와 세션/Lua 문맥 전환은 토큰도 해제한다.

캐시 적중 여부로 결과가 달라지지 않도록 문자·토큰·작업 예산은 매 분석에 동일하게 적용한다. 문자 접두부를 먼저 제한하고, 토큰 한도에서는 별도 제한 목록으로 helper의 lookahead도 막는다. 캐시 원본 목록은 수정하지 않는다. 읽기 재시도는 새 읽기·분기 문맥을 만들며 기존 토큰만 재사용한다. `Analyze`의 기존 4인자 reflection 계약도 보존한다.

PRD가 허용한 유한 추적·동적 대상·미지원 구문·조건의 불확실성은 제품의 명시적 지원 경계다. 모든 선택지를 Supported로 만들거나 모든 미래 결과를 얻어야 완료된다는 요구로 확대하지 않는다. 반대로 원본 호출의 존재만 확인한 검사를 조건 충족·확정 보상·전체 누락 없음의 증명으로 확대하지 않는다.

## 대조 방식과 확인 범위

공개 alpha.3 DLL의 SHA-256은 `f26a19d80495cfc24128a1b5cb2cd49bdad12e20f90cb632fe60a74e8ed8fb8f`다. 같은 원본 입력과 실제 DLL IL 경로로 새 후보와 대조한다. fixture는 Unity·리소스 읽기·이름 표시의 경계만 제공하고 파서·분석기·설명 구현은 후보에서 복사한다. 현재 플레이어 스냅샷은 비활성화한다.

경로를 받기 전 root-only 대조는 후속 읽기를 전부 Waiting으로 처리했다. 경로 확인 후에는 정확히 `story/chinesetraditional/` 접두부와 소문자 정적 대상만 조회하며 다른 언어·동명 파일로 폴백하지 않는다. Missing은 제공된 검증 집합 안의 부재와 실제 게임 로드 실패를 구분한다. 별도 Python 스캐너는 제품 파서를 import하지 않고 인덱스와 원본 호출의 owner/name/인자 해시 근거를 대조한다.

이 검사는 실제 Lua 본문을 입력으로 한 정적 대조다. Lua를 실행해 미래 결과를 얻는 검사가 아니다. 원본에서 호출 흔적이 있다는 결과는 모든 효과의 누락 없음, 정확한 조건 충족·동적 값·실행 순서나 저장 이후 값을 증명하지 않는다. 합성 회귀로 소유 범위·조건·다음 선택·재시도 경계를 별도 검사한다.

## 확정한 오프라인 정책과 비용

정확한 번체 이야기 2,198개의 최대 본문은 UTF-16 502,124자·86,919토큰이다. root 발견 상한은 524,288자·131,072토큰, 선택지 1,024개, 중첩 128, 본문 복사 누계 1,048,576자, 결정적 작업 2,097,152회다. 전체 후보에서 최대 본문 복사 누계는 813,296자였고 발견 한도 입력은 0이었다. 후속 추적의 누적 예산과 분리한다.

이번 소스에서 채택한 후속 정책은 **깊이 8 / 루트 포함 고유 스크립트 32 / UTF-16 1,310,720자 / 262,144토큰 / 결정적 작업 524,288회 / 입장 문맥 최대 128개**다. 캐시와 무관하게 같은 논리 예산을 청구한다. 이 값은 이번 자료와 macOS 정적 대역 검사에 근거한 제품의 오프라인 지원 정책이며 Unity 프레임 시간의 인증값은 아니다.

시간만 늘리거나 기본 한도를 무제한 높이는 방식으로 처리하지 않았다. 같은 예산의 FIFO는 얕은 경로를 살리지만 다른 경로가 밀릴 수 있어 전수 대조가 필요했다. 마지막 5개 호출의 해당 root 국소 복구 경계는 1,098,977자 실패 / 1,098,978자 성공이었다. 이는 이 자료·호출 집합의 관측값이며 일반적인 단조성·전수 최소를 증명하지 않는다. 선택한 1,310,720자는 여유를 두고 비교한 두 기준의 호출을 모두 보존한다. 더 큰 값은 142레코드를 추가하지만 비교 기준 보존의 추가 이득이 없어 채택하지 않았다. 한도 안에서도 모든 임의 Lua 효과를 찾는다는 뜻은 아니다.

최종 후보 두 실행의 전체 fixture 비용은 **13.217초·13.350초**, root p95 **25.049ms·24.839ms**, 최대 **448.280ms·440.823ms**다. 스레드 할당 p95 11,983,568바이트·최대 약 171.54MB다. 이전 로컬 `48220e…` 후보의 15.642초·15.918초, p95 약 33ms·최대 약 459~462ms·최대 할당 약 306.70MB와 구분해 비교한다. 이 비용은 root 안 모든 선택지 분석·설명·리플렉션·보고서 생성·JIT를 포함하며 실게임의 한 프레임 시간이나 상주 메모리가 아니다. 입력 SHA 검증·메모리 적재는 별도 준비 단계다.

토큰 할당 최적화 직전 `4e8f15…` 후보에서는 최대 비용 root(`ch8_2_5_10_break_start_01`, 7옵션·1,465레코드)의 정적 추출이 약 578ms였다. 보고서 수집을 분리해도 대부분이 추출 비용이므로 메타데이터 부하 탓으로 돌리지 않았다. tokenizer의 두 글자 연산자 판정에서 반복 `Substring`을 문자 비교로 바꾸고 연산자·EOF 회귀를 추가했다.

원본→실험본→실험본→원본 순서의 같은 root 계측에서 추출은 573.61/556.19ms→482.88/488.61ms, 추출 할당은 약 253MB→166.8MB로 줄었다. 시간 약 14%·할당 약 34% 개선이며 4회 선택지·효과·순서·설명·논리 예산은 같았다. **실험본과 최종 후보 DLL의 전체 바이트가 같다.** 원본 전체 SHA 검증·UTF-8 적재는 타이머 밖이며 reader는 검증한 메모리 조회만 한다. **최악 사례에서 약 0.49초의 동기 정적 분석 지연은 여전히 성능 한계**다. `artifacts/trace-completion/tokenize-char-lab/{manifest,summary}.json`과 최종 감사의 고정 SHA 연결을 근거로 삼으며 Unity 실행 시간으로 확대하지 않는다.

최종 누적 최대는 문자 1,310,720·토큰 228,301·작업 487,910·고유 스크립트 27로 유한 상한 안에 있다. 54개 한도 영향은 알려진 호출을 보존하면서 Partial로 표시하는 지원 경계다. 실제 Unity 비용을 모르는 상태에서 이 수치로 프레임 분할·비동기 실행의 필요성이나 불필요성을 확정하지 않는다. 표시를 위해 Lua를 실행하는 우회는 추가하지 않았다.

별도 고정 FIFO 초기 후보의 캐시 on 1회/off 2회는 비용을 뺀 효과·순서·분기·이유·설명 해시·논리 예산이 모두 같았다. 캐시 on 전체 13.43초·할당 합 약 8.10GB, off 15.62/15.53초·약 10.43GB였다. 이는 캐시의 정적 재사용 효과를 보여주는 대역 실험이며 최종 후보의 Unity 성능이나 상주 메모리를 보증하지 않는다. 실험 사본의 무인자 캐시 생성자만 바꾸고 제품·원본은 수정하지 않았다.

예산 실험·경계·3선택지 소속 대조는 `artifacts/trace-completion/audit/`, 최종 DLL 반복·독립 스캐너·기준 identity 비교는 `optimized-audit/`에 있다. 빌드와 겹친 중간 프로필의 비용은 최종 비용으로 승계하지 않는다.

PRD #2·기능 전체를 완료 처리하거나 이슈를 닫지 않았다. 사용자 지시로 이 후보와 같은 DLL을 `v1.0.4-alpha.4` prerelease로 게시하고 공개 다운로드를 검증했다. [배포 기록](RELEASING.md)에 게시 결과를 구분하며 이 문서의 후속 커밋은 소스 태그·공개 자산을 바꾸지 않는다.
