# 지도·선택지의 마커 준비 표시 — alpha.35

main의 기준은 `fdce0c702d149b17c7f1798ff86ab835605dd149`다. [후보·검사·설치](ISSUE-6-ALPHA35-RELEASE.md)와 [실제 Windows 확인표](ISSUE-6-WINDOWS-VALIDATION.md)를 구분한다.

## 표시 규칙

포커스 시 나오는 `이 장소의 안내를 확인하는 중` 툴팁과 첫 조회의 일반 대기 문구를 제거했다. 지도 장소와 실제 활성 선택 버튼의 마커 위치에 작은 금색 원형 스피너를 표시한다. 포커스나 마우스 호버는 필요 없다. 실제 대화·경로·기회가 있을 때의 내용 툴팁과 금색/아이보리 두루마리 마커는 유지한다.

| 현재 표시 판단 | 화면 |
| --- | --- |
| 기존 예산에서 초기 자료·색인·경로 확인이 대기/진행 중 | 같은 항목이0.2초 이상 대기하면 스피너 |
| 현재 표시할 마커 근거를 찾음 | 해당 항목의 스피너를 제거하고 마커 |
| 지원하는 조회를 마쳐 현재 표시할 안내가 없음 | 스피너·마커 모두 숨김 |
| 읽기 실패·미지원·상한·현재 자료 미확인으로 보류 | 계속 돌지 않으며 사유는 기존 지도 로그에서 조회 |

스피너 종료나 마커 없음은 전체 게임에 이벤트가 없다는 증명이 아니다. 금색의 대기 임무/증명1회성과 아이보리의 일반 대화/경로 안내는 기존 기준을 따른다. 표시할 경로 하나를 확인했으면 다른 후속 경로 전체를 기다리지 않고 마커를 우선한다. 금색 기회를 일반 경로 안내로 대신 증명하지 않는다.

같은 항목의 대기 시간은0.25초 스냅샷 교체나 포커스 이동으로 재시작하지 않는다. 이미 확인한 마커를 정상 갱신마다 스피너로 되돌리지 않는다. 실제 입력 변경·새 정의 준비가 필요할 때는 기존 판정을 다시 확인한다. 준비가 끝난 빈 항목은 계속 회전하거나 대기 툴팁을 띄우지 않는다.

## 같은 조회 결과에서 발행

MapMarkerSnapshot과 ChoiceStorySnapshot의 Preparing에는 기존 조회가 아직 준비 중인 실제 anchor만 담는다. 마커가 없다는 이유만으로 모든 항목을 대기로 간주하지 않는다. 지도는 등록된 보이는 최대64장소를 기존 순서/공유 예산으로 처리하며, 새 코드가 장소 검색·Lua 준비를 별도로 시작하지 않는다. 선택 메뉴는 관찰한 실제 활성·조작 가능 버튼 중 최대256개만 사용한다.

지도 경로의 초기 후보 색인과 첫 검사 범위를 추적해 여러 번의 예산에 나뉘는 음성 결과도 끝나게 한다. 이 진행 기록은 **조건 판정의 음성 캐시가 아니다.** 기존 현재 조건 재확인은 계속하고, 나중에 해금된 경로도 다시 찾는다. 긍정 경로의 ReadStamp 검증·해금·완료·반복 활동·진입 상태·행동력·임무 우선순위는 바꾸지 않는다. 설치 파일 준비 여부도 작업 상태를 읽을 뿐 새 파일 읽기를 시작하지 않는다.

1회성만 켠 경우에는 기존에 선택 장소 조회가 예약한 경로/결과 준비만 표시한다. 스피너를 위해 미선택 장소의 결과 분석을 새로 시작하지 않는다. 이미 준비한 기회/대기 임무 마커가 있으면 추가 회전을 하지 않는다. 실패나 정보 부족을 무한 대기로 숨기지 않으며 기존 상세 진단·5초 재시도를 유지한다.

렌더러는 같은 발행 결과에서 스피너와 마커를 읽는다. 선택 장소의 요약이 아직 비어 있어도 이미 확인한 마커 결과를 지우지 않는다. 더 새로 확인한 선택 장소 마커가 있으면 회전보다 우선한다. 데이터 조회·판정·갱신은 렌더러에서 실행하지 않는다.

## 그리기·수명·입력

InformationLoadingState는 anchor의 참조 동일성과 문맥을 기준으로 지연만 관리한다. 저장/메뉴 문맥 변경·시간 역행·유효하지 않은 시각에서 초기화하고, 완료/실패/숨김/OFF 대상의 참조와 시간을 정리한다. 상태·로그·팝업 가림, 애플리케이션 포커스 상실, 화면 밖·비활성·조작 불가 항목에는 그리지 않는다. 숨김 후 돌아오면 대기 지연을 새로 시작한다.

스피너는 코드가 만든32×32 이미지8프레임, 총32KiB RGBA다. 보이는 지연 항목이 처음 생겼을 때 텍스처 하나로 올리고 모든 항목이 공유한다. Repaint에서는 UV만 바꿔 항목당 한 번 그린다. 매 프레임 그림 생성·텍스처 업로드·폰트 검색·파일 접근·전체 분석을 하지 않는다. 실제 게임 그림이나 외부 모드 이미지를 가져오지 않으며 설치 파일도 늘리지 않는다. 업로드 실패 시 해당 수명에서 반복하지 않고 기존 배지 해제 경계에서 텍스처를 정리한다.

새 클릭 영역·raycast·포커스·선택·입력 소비를 추가하지 않는다. Xbox/XInput·키보드·마우스·터치·입력 소유권/해제/중립 보호, #5 이벤트/예약·로그 네 탭·주사위·상점·실제 분기를 유지한다. 설정 키/기본값·cfg·정상0.25초/실패5초·숨김/OFF 중단·공유 준비5ms·Lua1개/8192작업·정상 웜 주기 Lua 재분석 없음과 읽기 전용 계약은 그대로다.

## 검사·성능 근거

생산 provider/경로/표시 코드를 연결한 관리 검사에서 항목별 초기 대기, 미포커스 지도/버튼, 양성의 즉시 전환, 빈 항목/실패 종료, 다중 예산 음성 검사 종료, 이후 해금 복구, 마커 유지, 활성/가림/OFF/문맥·시각 변경과 입력 불변을 검사했다. 실제 UI 코드의 표시 경계 검사에서0.2초 지연·공유 텍스처1회 업로드·프레임 UV 변경·Repaint 전용·기존 마커/내용 툴팁과의 공존을 확인했다. 새 타입을 별도 UI 검사 프로젝트에 연결하는 초기 fixture 오류를 보완한 뒤 전체 검사를 다시 수행했다. 원래 실패 로그와 최종 로그는 로컬 artifacts/issue-6/loading-indicators/에 보존한다.

alpha.34 소스와 현재 소스를 읽기 전용으로 비교한 같은 관리 벤치마크에서8/32/64장소·선택/미선택·직접/깊은 경로·조건 목록0/4096개의18개 표본 모두 첫 마커/전체 표시까지의 조회 횟수와 초기 Lua 읽기 횟수가 같았다. 모든 표본의 정상 웜 자원 읽기는0이고 초기 조회당 Lua 읽기는 최대1개였다. 전체64개의 깊은 경로는 두 버전 모두192회 조회에서 표시됐다. 조회 간격을 늘릴 근거는 없어0.25초를 유지한다.

예를 들어 조건 목록0개의64장소에서 웜 p95는 미선택0.454→0.447ms, 선택0.508→0.546ms, 깊은 경로0.813→0.854ms였다. 표본·JIT·동시 빌드 영향을 받는 한 차례 관리 측정이므로 속도 향상이나 정확한 회귀율을 주장하지 않는다. 정상 스냅샷의 추가 할당은 약40바이트 수준이었다. 별도 상태 관리100,000프레임×64anchor 측정은428.15ms, 약0.0043ms/프레임이며 Stopwatch 객체40바이트를 제외한 루프 할당은0이었다. 이 측정은 Unity geometry/GPU 그리기 비용을 포함하지 않는다.

실제 설치 DLL 연결·전체21개 검사·고정 커밋/ZIP 재검증은 [릴리스 기록](ISSUE-6-ALPHA35-RELEASE.md)에 기록한다. Windows/Unity/Harmony·사용자 세이브·물리 입력·FPS/GC와 실제 게임 화면의 시인성은 아직 확인하지 않았다. 사용자 확인 전 #6 전체 완료나 이슈 종료로 처리하지 않는다.
