# PRD #6 후속 지도 안내 개선 분석

[현재 구현](ISSUE-6-IMPLEMENTATION.md) · [공개 alpha.2의 범위](ISSUE-6-SELECTED-MAP-SHOP.md) · [현재 main의 상점 변경](ISSUE-6-SHOP-DESCRIPTION.md) · [개발 안내](DEVELOPMENT.md)

분석일: 2026-10-21. 기준 소스: main `5e951cf8a37fb9b114380d8548626775b1045d23`. **이 문서는 조사 결과와 구현 제안이며, 아래 지도 개선은 아직 구현하지 않았다.** 새 후보 빌드·게시·Windows 확인·#6 완료의 근거로 사용하지 않는다. 원래 작업 폴더의 main에서만 조사했으며 제외한 alpha.3을 복원하지 않았다.

## 결론

후속: 사용자가 이 설계의 main 구현·커밋·prerelease를 요청했다. 아래는 구현 전 조사 당시의 기록이며 실제 반영·검사·남은 Windows 확인은 [후속 구현 기록](ISSUE-6-MAP-GUIDANCE-RELEASE.md)에 구분한다.

조활 시스템에서 유용한 부분은 임무·기회를 모으는 기준과 상태 구분이다. DiceMaster는 선택 장소 패널 하나와 기존 패드 로그 탐색을 유지하면서 이를 개선할 수 있다. 단순히 라벨을 바꾸거나 현재 Position 풀 검색을 재귀 호출하는 것으로는 해결되지 않는다. **대기 임무와 조건 후보의 구분, 메뉴 경로 모델, 중복 없는 항목 목록**이 먼저 필요하다.

기본 목록은 현재 단계 임무와 안전하게 판별한 1회성 기회를 중심으로 구성하고, 일반 활동·고정 이야기·1회성 미확인 항목은 상세의 별도 묶음에 남기는 방향을 제안한다. 판별 불가를 반복 가능으로 바꾸거나 불완전 탐색을 ‘없음’으로 표시하지 않는다. 자동 패널은 이름·종류·상태만, 경로·조건·효과는 기존 로그에서 읽는 계약을 유지한다.

## 실제 게임 계약에서 확인한 주의점

### 시작 스크립트는 현재 기본 자료를 읽는다

제공된 게임의 `PositionController._scriptName`은 코드상 초기값이 빈 값인 직렬화 필드이며 클릭 실행 중 난수·조건 플래그 처리가 끝난 뒤에만 갱신된다. 선택·hover·초기화에서 갱신되지 않아 비어 있거나 이전 실행 값일 수 있다. 비교 소스의 이 필드 사용을 복제하면 잘못된 시작점이 된다.

현재 DiceMaster의 `_positionData._defaultScript` 읽기를 유지한다. 제공 DLL의 `FreePositionData.GetExecuteScript(float)`도 이 필드만 반환한다. 현재 기본 스크립트가 비었을 때 과거 `_scriptName`으로 대체하지 않는다. 값을 준비하려고 클릭·GetRandomResult·SetConditionFlag·GetExecuteScript를 호출하지 않는다. 클릭 처리 중 활동 스크립트 진입 전에 일어나는 플래그 변경도 표시기에서 실행하거나 현재 조건에 몰래 반영하지 않는다.

### 기존 대기 상태와 현재 조건은 서로 다른 정보다

`MainMissionStart`, `MainCheckData`, `ActiveSubMissions`의 제공 getter는 필드 반환뿐이다. 기존 관리 객체에서 이 값을 읽을 수 있지만 `MissionManagerData.Instance`는 지연 Unity 검색이므로 사용하지 않는다. UpdateCheckMissions·UpdateActiveSubMissions·GetActiveMissions는 플래그·시간·현재 키·대기 목록을 변경하는 경로이므로 호출하지 않는다. MissionCheckData.Check 자체는 조건·기간 판정이지만 난수를 포함할 수 있는 게임 조건 체인을 실행하므로 표시용으로 호출하지 않는다.

- 주 임무의 현재 키가 다음 단계나 clear로 이동한 뒤에도 `MainCheckData`에는 기존 대기 단계가 남을 수 있다. 현재 키만 보고 대기 항목을 지우지 않는다.
- 부 임무 사전의 키는 `MissionData._name`이라는 논리 ID다. 번역명이나 Unity asset name으로 대응시키지 않는다.
- 조건을 지금 만족해도 기존 대기 사전에 없으면 **조건 충족 후보**다. 반대로 대기 항목의 현재 조건이 달라졌어도 실제 장소 클릭은 그 조건을 재검사하지 않는다. 대기 사실과 현재 조건 결과를 함께 기록한다.
- 기존 명시적 미션 예약도 같은 사전의 값을 교체한다. 모든 대기 항목을 순수 네이티브 판정 결과나 최종 선택 완료라고 설명하지 않는다. 표시 경로는 예약·취소를 실행하지 않는다.
- 같은 사전·같은 개수·같은 키에서도 값이 교체될 수 있다. 참조와 개수만으로 대기 상태를 캐시하면 안 된다.

### 장소 클릭과 장소 무관 임무의 실행 경로가 다르다

장소 클릭은 장소 활성·FreeManager 처리 중 여부를 먼저 확인한다. 배치된 주 임무가 대기하면 일치하는 장소만 주 임무를 실행하며 **행동력을 검사하지 않는다**. 그 외에는 행동력을 확인한 후 같은 장소의 첫 대기 부 임무를 사용하고, 없을 때 일반 활동으로 간다. 부 임무의 현재 조건·기간·active는 이 클릭 경로에서 다시 검사하지 않는다.

`PositionType.無 == 0`은 장소 무관 자동 경로다. 제공 구현은 주 임무 전 부 임무 → 장소 무관 주 임무 → 주 임무 후 부 임무 순서로 살핀다. 선택 장소의 행동력·활성·처리 중 제한을 이 묶음에 적용하지 않는다. 실제 호출 시점이 있으므로 자동 경로 대기도 즉시 실행 보장은 아니다. 이 순서를 살피려고 HasAnyMissionTrigger·HasSubMissionTrigger를 실행하지 않는다.

기간은 제공 게임 IL을 따른다. 특정 시점은 연·월·단계 일치, 구간은 양 끝 포함 비교다. `TimeCheckType` 3인 주기형은 제공 구현에서 `_periodStage`를 검사하지 않는다. 표시기가 독자적인 월 단계 제한을 만들어서는 안 된다.

## 표시와 항목 모델 제안

자동 패널은 선택한 장소 이름 아래 현재 관련 항목만 간결하게 표시한다. 예시 문구는 `대기 임무 1 · 단계 후보 2 · 확인된 1회성 1`이다. 대기 항목도 다른 주 임무·행동력·같은 장소 우선순위 때문에 이번 클릭에서 실행되지 않을 수 있으므로 이름 옆 상태로 구분한다. 세 집계는 같은 단계/이벤트를 중복 계산하지 않는다. 장소 무관 수는 선택 장소 수에 섞지 않는다.

| 분류 | 기본 목록·요약 | 상세에서 보존할 내용 |
| --- | --- | --- |
| 기존 대기 임무 | 표시, 현재 키가 이동해도 유지 | 대기 단계·현재 조건·실제 클릭 우선순위·방해 사유 |
| 현재 단계 후보 | 대기 항목과 중복 제거 후 표시 | 조건 충족/미충족/확인 불가·기간·대기 미확인 |
| 안전하게 증명된 1회성 | 확인된 기회로 표시 | 경로·조건·가중치·증명 근거, 임의 선택 가능성과 실제 선택 결과 구분 |
| 1회성은 증명됐으나 경로 불명 | 확인 필요 상태, 현재 가능 수에서 제외 | 미지원 경로·선행 변경·탐색 제한 사유 |
| 일반 활동·고정 이야기·1회성 미확인 | 기타 연결 정보에 보존, 기본 후보 수에서 제외 | 확인된 연결·일반 활동 여부·증명 불가 사유 |
| 장소 무관 임무 | 지도 로그의 별도 묶음 | 주 임무 전/주/후 경로·기존 대기/현재 단계·현재 조건 |
| 읽기 실패·준비 중·제한 도달 | 상태를 반드시 표시 | 성공 0건과 구분, 이전 값은 같은 문맥의 이전 값임을 명시 |

미래 단계 전체를 사전처럼 나열하지 않는다. 현재 단계가 기간 밖이면 상세에 사유를 남기고 지금 기회 수에는 넣지 않는다. `1회성 확인 불가`는 반복 가능을 뜻하지 않는다. 해당 경로에서 활성 조건을 깨는 확정 결과라는 의미이며, 미독·영구 소멸·다른 경로에서의 재활성화 불가까지 증명한 것은 아니다.

중간에 메뉴 선택이나 이동이 필요한 경로는 `선택 후 기회`, 조건·선행 변경을 안전하게 평가하지 못하면 `경로 확인 필요`로 표시한다. 활성 조건과 양수 가중치를 확인해도 랜덤 결과의 선택을 보장하지 않는다. 선택 장소가 진입점인 다른 장소의 경로는 이동 경로를 상세에 밝혀 현재 장소에서 즉시 일어나는 것처럼 표시하지 않는다.

현재는 provider가 모든 후보를 합친 InformationRow 하나를 반환하고, 로그가 그 상세 문자열 전체를 한 행으로 받는다. 오버레이에는 `map.Rows.Count == 1` 전제도 있다. provider를 여러 DisplayQuery로 바꾸기만 하면 기존 패널이 사라질 수 있다. **갱신 단위 하나의 MapGuideSnapshot에 요약과 종류별 항목 목록을 함께 넣고**, 오버레이는 요약, 로그는 개별 항목을 게시하도록 바꾸는 편이 적합하다. 한 시점의 같은 자료를 공유하며 행마다 재분석하지 않는다.

로그는 기존 지도 안내 조회 안에서 선택 장소·장소 무관·기타 연결 정보를 종류 표시한 행으로 제공한다. 기존 방향키/왼쪽 스틱 행 이동·오른쪽 스틱 상세 스크롤·B 복귀·LB/RB 탭 이동을 유지한다. 실행 Target·예약 ticket은 만들지 않는다. 새 입력 체계·hover 전용 팝업·전체 지도 표식을 추가하지 않는다.

장소 미선택이어도 살아 있는 현재 지도 세션을 이미 관찰했다면 로그에서 장소 무관 항목을 읽을 수 있어야 한다. 이를 위해 기존 lifecycle에서 얻은 관리 객체·지도 수명을 별도로 유지하고 MapGuideSource.Visible/ContextKey/Discover의 ‘선택 장소 필수’ 전제를 조정해야 한다. 지연 singleton·숨은 Unity 객체 검색·매 주기 전체 장소 순회는 사용하지 않는다. 지도 밖이나 관리 자료 미준비는 대기로 표시하고 지난 지도 자료를 현재 값으로 남기지 않는다.

## 후속 메뉴 탐색 설계

현재 `ExtractPositionWorkFromLua`는 문자열·주석을 제외한 호출 키 수집기다. 함수 내부·조건문·루프·return 뒤·재할당된 manager까지 도달 가능한 것으로 입증하지 않으므로, 이 결과를 재귀 확장하는 방식은 부적합하다. 기존 호출자의 동작은 보존하고 별도 경로 API를 추가한다.

1. 현재 기본 스크립트에서 출발해 정확한 번체 리소스 키만 읽는다. 등록된 리터럴 후속 스크립트, 실제 선택 분기, 소비된 Position 반환값의 풀과 결과 스크립트를 제한적으로 연결한다. 원문 범위·선택/분기 ID·부모 조건·선행 명령을 보존한다.
2. 값은 `LiteralScript(key)`, `PositionPoolResult(poolId, callSite)`, `Unknown`으로 추적한다. `var1 = checkpointmanager.Position("Pool"); luamanager.SetNextScript(var1)`를 난수 실행 없이 연결한다. 버려지거나 덮어쓴 반환값은 실행 경로로 세지 않는다.
3. 변수 scope·manager 바인딩·재할당·조건부 등록·마지막 등록 우선·빈 등록 취소·return별 종료 상태를 처리한다. 함수/콜백 본문과 루프를 임의 실행·전개하지 않는다. 미지원 호출·선행 상태 변경 뒤에는 현재 조건을 미래 조건으로 확정하지 않는다.
4. 선택지 별칭은 원문 범위와 실제 choose/branch 정체성으로 합친다. 옵션 문자열이나 현재 OptionBlocks 개수로 집계하지 않는다. 이벤트는 풀/항목/결과 스크립트의 안정된 ID로 한 번 세고 여러 도달 경로는 상세에 보존한다. 임무는 논리 임무 ID와 유효 단계 ID를 사용한다.
5. 정의 그래프와 현재 조건 읽기를 분리한다. 기존 PreviewConditions·EventEligibility·SwitchEligibility의 안전한 필드 해석을 재사용하며 Position·Switch·Condition·GetResult·GetRate·Check·Execute를 호출하지 않는다. 알려진 실패 경로만으로 불가를 확정하고, 남은 경로가 미확인이면 불명을 남긴다.
6. 경로 도달성과 1회성 증명은 독립시킨다. 종단 이벤트의 명시 활성 조건과 기존 OneShotProof를 사용한다. 후손에 1회성이 있다는 이유로 부모 선택지 자체에 1회성 표식을 붙이지 않는다.

실제 표본에서 `room_001`은 직접 Position 풀이 0개지만 수면 선택 → `room_001_break_option` → `Room_Work_001` 반환 변수 → 후속 등록이 있다. `door_001_01`의 직접 풀 1개 외에 6개 목적지 스크립트에 7개 추가 풀 이름이 연결된다. 이는 문법상 연결이며 현재 가능한 이벤트 8개라는 뜻이 아니다. `pharmacy_01_01`은 Position 반환값을 받은 뒤 Switch에 따라 특수 리터럴 스크립트 또는 그 변수를 등록한다. 리터럴만 추적하거나 풀을 평면 합집합하면 누락·과장이 생긴다.

표본 9개에서 현재 OptionBlocks가 반환한 25개 블록은 모두 Conditional=true다. `door_001_01`의 실제 9개 선택은 문자열 별칭 때문에 11개 블록으로 나타난다. 이 bool과 별칭 키만으로 현재 경로 조건이나 항목 정체성을 복원할 수 없다. PreviewSyntax에 경로용 원문 범위/정체성을 추가하되 기존 효과 설명의 의미와 공개 분석기 서명은 보존한다.

기존 OneShotProof는 Issues·선택·조건부·후속·실행 불명 결과를 거절한다. 따라서 경로 그래프만 추가해도 양성 표식이 바로 늘어난다고 보장할 수 없다. 시각·대사·대기 API도 콜백·제어 흐름·상태 변경을 실제 IL로 개별 감사한 뒤 안전한 호출만 처리해야 한다. 이름만 보고 무해하다고 허용하거나 Issues를 버리는 우회는 하지 않는다. 추후 선택을 포함해 증명하려면 가능한 모든 완료 경로가 활성 조건을 깨는지 입증해야 하며, 일부 경로의 플래그 변경만으로 확정하지 않는다.

## 캐시·성능·실패 상태

- 정상 0.25초·실패 5초·숨김/OFF 조회 0·정상 주기 Lua 로드/재분석 없음 계약을 유지한다. 정적 구문/경로/풀 정의와 현재 대기 사전·플래그·조건 결과를 별도로 소유한다.
- 대기 사전의 작은 현재 내용과 MainMissionStart·MainCheckData·현재 키 등은 정상 갱신에서 다시 읽는다. 정적 임무 정의 색인의 참조/개수 캐시로 현재 대기 상태까지 대체하지 않는다. 실패 재시도 revision도 대기 값 교체를 포함해야 한다.
- 기존 정의 색인은 불변 asset 정의를 전제한다. 같은 목록의 슬롯 교체·같은 asset의 단계 배열/위치 변경까지 임의 지원하려면 관찰 가능한 별도 revision/무효화 정책이 필요하다. 이를 위해 정상 주기마다 전 임무를 재탐색하지 않는다.
- 선택 세대·지도 세션·관리 객체·기본 스크립트/풀 자료·Lua 문맥/언어 등 소스 문맥이 바뀌면 이전 게시 권한을 폐기한다. A→B→A도 오래된 A를 게시하지 않는다. 저장/로드·새 게임·장면 종료·관련 OFF에서 경로와 증명 참조를 정리하고 과거 내용을 재생하지 않는다.
- 그래프가 커지는 첫 조회를 하나의 Update에서 끝내지 않는다. 토큰화·scope 분석을 포함한 준비 작업의 재개 단위를 설계하고 준비 중을 게시한다. 숨김/OFF에는 준비도 중단한다. 노드 수만 나누고 기존 큰 Tokenize 호출을 그대로 동기 실행하면 첫 멈춤이 해결됐다고 할 수 없다.
- 초기 논리 한도는 기존 trace의 깊이 8·서로 다른 스크립트 32·문맥/대기열 128·누적 1,310,720 UTF-16 문자/262,144 토큰/524,288 작업을 기준으로 삼는다. 선택 노드 1,024·종단 항목 256 등 경로 전용 상한과 아직 읽지 않은 큐의 상한을 추가하는 안이다. 확정 성능 수치가 아니며 실제 자료에서 조정한다. 개별 구문 분석의 문자/토큰 제한도 유지한다.
- 순환·누락·미지원·상한 도달은 완전한 0건이 아니다. 완전성 상태를 스냅샷에 넣고 확인한 항목과 빠진 범위를 구분한다. 동일 문맥의 이전 성공값은 실패 상태와 함께만 보여주며 다른 장소·세션 값은 재사용하지 않는다.
- OnGUI는 게시된 문자열·배치만 읽는다. 전체 지도 투영·장애물 조합 탐색·모든 장소 조건 읽기를 되살리지 않는다. 실제 프레임 비용은 Windows에서 별도 측정한다.
