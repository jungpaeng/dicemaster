# 지도 대화 마커의 준비·입력 확인 — alpha.33

[후보·설치·게시](ISSUE-6-ALPHA33-RELEASE.md) · [Windows 확인표](ISSUE-6-WINDOWS-VALIDATION.md)

## 원인과 변경

검은 기회 표식은 실제 등록 대기 임무 또는 준비된 엄격1회성의 현재 도달성에서 온다. 흰색은 장소의 Lua와 연결 경로·해금·완료·활동 분류·가상 진입/초기화를 확인해야 한다. alpha.32의 지도 준비는 현재 메뉴와 후속 일을 같은 큐에 넣었고, 0.25초마다 하나의 장소만 준비했다. 첫 표시가 불필요한 후속 일 뒤로 밀렸다.

각 조회는 새 MapMarkerSnapshot을 만든다. 이전 성공 경로를 먼저 재판정하지만 약5ms 시간 예산이 끝나면 미방문 장소가 새 목록에서 빠져 표시가 사라졌다. 11장소·게임 값 불변의 합성 경계에서 조건 읽기 지연을 주자 매번6~7개만 남는 깜빡임을 재현했다. 별도의64장소·3단계 경로에서는 성공32개가 조건 예산128을 전부 소비해 나머지 탐색이 진행되지 않았다.

지도에도 선택 화면의 PrioritizeRootPreparation을 적용해 현재 메뉴를 먼저 닫는다. 기존 성공 경로의 입력 검증은 선택적 준비보다 먼저 처리하고, 입력이 같은 성공 경로는 신규 탐색의 경로/조건 슬롯을 쓰지 않는다. 준비/신규 경로 탐색 자체의 시간·작업·리소스 상한은 늘리지 않는다.

## 재사용의 정확성·상한·수명

PreviewConditions.ReadStamp는 일반 지도 경로의 성공한 읽기에서만 만든다. 조건 구조의 필드·기존 native 소유자/입력 참조·읽은 현재 값, 배열 구성, List의 revision, 로드 자료 출처, 감사된 raw Lua 연결과 경로 준비 여부를 기록한다. 다음 조회에서 같은 읽기 계획으로 관련 값과 참조를 확인하고 모두 같을 때만 판정·경로 문자열·InformationRow를 재사용한다. 고정 카탈로그 이름·파일 정의는 기존 정의 캐시의 문맥 내 불변 메타데이터 계약을 따른다. 전체 플래그나 모든 임무를 검색하지 않는다.

실패한 후보를 앞서 조사한 경우에는 그 실패 입력까지 성공 경로에 붙이지 않는다. 다음 우선 조회에서 성공 경로만 따로 기록한다. 최대1024개의 관찰, 배열256셀, 최대64개의 보이는 장소로 제한하며 지원하지 않는 구조·읽기 실패·서로 다른 샘플·상한 초과는 재사용을 거절한다. 같은 LuaEnvironment 안의 interpreter 교체와 관찰 연결 해제도 무효화한다. 능력치 FinalValue를 재확인할 때는 기존 재귀 변환 검증을 먼저 거쳐 순환 그래프를 직접 호출하지 않는다. 현재 Reader/가상 상태를 저장하지 않고, 게임의 setter·Condition/Switch/Execute·Reset·RNG·Lua 실행도 호출하지 않는다. 엄격1회성·기회 판정은 이 캐시를 쓰지 않는다.

장소 활성·행동력·처리 중·주/보조 임무 우선순위는 매번 먼저 확인한다. 관련 값·조건/목록·소유자·진입/초기화 자료·완료 상태가 바뀌면 성공 계획을 버리고 새로 판정한다. 변경/실패를 계산 대기로 덮어 양성을 유지하지 않는다. 성공하지 않은 경로의 false 결과를 영구 캐시하지 않아 새 해금도 재발견한다.

소스·Lua 문맥·로드·장면·새 게임·설정 OFF·종료에서 기존 Source와 함께 제거한다. 숨김·가림·포커스 상실·OFF에는 조회/입력 검증을 하지 않는다. 설정 키/기본값/cfg는 그대로이며 패드·키보드·포인터·터치·해제/중립 입력을 추가하지 않는다.

## 예산과 성능 해석

정상0.25초/실패5초를 유지했다. 새 정의 준비는 화면 전체 Lua1회/풀1회·8192작업·협력식 약5ms다. 성공한 표식의 제한된 입력 확인은 이 선택적 준비의 마감보다 먼저 처리한다. 따라서5ms는 전체 조회·프레임의 하드 상한이 아니다. 값 읽기 비용·JIT·native I/O·GC까지 항상5ms 안에 든다는 주장은 하지 않는다. 예산만 소진됐다는 이유로 변경 없는 기존 표식을 누락하지 않으면서도 값 변경은 직접 확인한다.

공개 tools/benchmark-guidance-markers.py는 8/32/64장소, 무관 정의0/4096개, 미포커스/선택+배경/3단계 경로를 비교한다. 300회 준비 뒤200회 측정이며 baseline은68772fd다. macOS arm64/.NET8의 관리 게임/Unity 경계이고 Windows 렌더/FPS·세이브 실측이 아니다.

| 표본 | alpha.32 p95 ms | alpha.33 p95 ms | 표시/할당 |
| --- | ---: | ---: | --- |
| 짧은 경로·미포커스 | 0.090–1.787 | 0.048–0.509 | 모두8/32/64 유지, 약58–445KB →14–95KB/조회 |
| 짧은 경로·선택+배경 | 0.094–1.897 | 0.059–0.562 | 모두8/32/64 유지, 약67–455KB →19–100KB/조회 |
| 3단계·64장소 | 0.771–0.780 | 0.777–0.929 | 이전32개에서 정체 → 새64개 유지, 신규 전체192회 갱신 |

64장소·3단계의 CPU 비교는 출력 수가 달라 같은 작업량의 속도 대결이 아니다. 작은 정의64장소에서는 새 p95가 약간 커진 표본도 있으며 모든 경우가 빨라졌다는 주장은 하지 않는다. 모든 warm 표본에서 Lua 재읽기0, cold 한 갱신 Lua1회 이하를 유지했다.

실제 복제본의 당문11장소 Lua/정의를 모두 제공하고 현재 상태는 명시적 기본값으로 설정한 별도 관리 검사에서도 세 번 같은 결과를 얻었다. 남제자방 첫 표시34→15회, 강경단39→21회, 여제자방14회·연단방18회는 같았다. 갱신 주기 환산은 가능하지만 사용자 Windows의 실제 초·세이브 결과가 아니다. 파일 worker가 있는 검사는 인위적 가상 시계와 실제 worker 시간이 다르므로 첫 갱신 수를 사용자 대기 시간으로 바꾸지 않는다.

## 자동 검사와 남은 확인

새 회귀는11/64장소의 전체 발견·warm 행/성공 계획 재사용, 이미 만료된 준비 마감에서 표시 유지, 하위 해금 false·조건 필드/동일 길이 목록 교체·행동력/가시성 변경 즉시 제거를 검사한다. 별도로 입력 읽기 실패·배열/목록 내부 변경·관찰 상한·시간/능력치 변화 무효화를 확인한다. 기존 초회 완료·반복 활동·후속 해금·현재AND false·초기화/진입 projection·cold file fallback 검사를 유지한다.

전체 실제 DLL·패키지·고정 커밋 재빌드 결과는 [배포 기록](ISSUE-6-ALPHA33-RELEASE.md)에 확정한다. 실제 Windows의 첫 표시·장시간 깜빡임·FPS/GC·사용자 저장·물리 입력은 확인 대기이며 PRD #6을 종료하지 않는다.
