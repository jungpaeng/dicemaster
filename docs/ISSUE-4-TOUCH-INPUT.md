# PRD #4 후속: 패드 모드에서 로그 터치 입력 복구

2026-10-19 KST. 사용자가 패드 모드에서도 기존처럼 화면을 터치해 로그를 조작하도록 복구를 요청한 로컬 후보다.
에이전트는 게임을 설치하거나 실행하지 않았다. 실제 Windows 터치 기기 확인·공개 게시·이슈 #4 완료는 대기 상태다.

## 조사한 코드 경로와 확인 한계

기존 경로에는 게임의 패드 모드 커서 잠금·숨김이 로그에서도 유지되는 문제와, 마우스 이벤트 위주의 버튼 검사가 있었다.
터치·클릭으로 게임 입력 모드가 바뀌면 일괄 초점 초기화가 진행 중 누름→해제나 검색 편집을 취소할 수도 있었다.
이들은 로그 조작이 막힐 수 있는 코드 경로이며, 사용자 기기에서 실제로 어느 경로가 원인이었는지는 별도다.
당시 커서 상태와 OS 터치가 Unity에 전달한 실제 이벤트는 확인하지 못했으므로 기기별 원인을 단정하지 않는다.
제공 게임 DLL의 `PlayerInputController.OnControlsChanged`는 패드 모드에서 커서를 잠그고 숨긴다.
[Unity 2020.3 커서 문서](https://docs.unity3d.com/2020.3/Documentation/ScriptReference/Cursor-lockState.html)도 잠긴 포인터의 중앙 고정·숨김과 초점 변화 시 상태 재확인을 설명한다.

## 로그 수명에 한정한 커서 접근

`LogCursorScope`는 로그가 열려 있고 게임 창에 초점이 있을 때만 커서를 임시로 `None` 잠금·표시 상태로 둔다.
진입 시 실제 커서 잠금·표시 값을 저장하며, 별도 사용자 설정이나 게임 입력 모드를 새 원본으로 만들지 않는다.
로그 닫기·게임 초점 상실·플러그인 비활성화·종료 시 임시 소유권을 해제하고 복원한다.

- 같은 임시 `None`·표시 상태를 다음 프레임에 읽었다고 원래 복원 값을 덮어쓰지 않는다.
- 게임이나 다른 코드가 잠금·숨김을 다시 요청한 것이 관찰되면 복원 대상으로 기록한다.
- 이미 알려진 패드↔키보드·마우스 모드의 실제 변경이 관찰되면 그 모드에 맞춰 복원 대상을 갱신한다.
- 같은 시점에 실제 외부 커서 요청이 관찰되면 모드에서 추론한 기본값보다 그 요청을 우선한다.
- 처음 불명이던 모드를 나중에 읽은 것만으로는 실제 모드 전환으로 판단하지 않는다. 기존 커서 스냅샷을 보존한다.
- 닫기 직전의 외부 커서 변경도 관찰한다. 관찰할 수 없는 동일 값 재요청까지 식별한다고 보장하지 않는다.

모드 조회는 계속 읽기 전용이다. `OnControlsChanged` 호출, 게임 모드 강제 전환, 게임 액션·액션 맵 변경은 하지 않는다.
원 PRD의 **모드를 조회하기 위한 강제 변경 금지**와 별개로, 이번 사용자 요청에 따라 열린 로그의 포인터 접근만 임시 복구한다.
다른 앱이나 OS의 입력 설정을 변경하지 않는다.

## 모드 변화와 진행 중 포인터 입력

`LogPadFrame.PreservePointerTransaction`은 모드 변화나 포인터 사용 전환으로 생긴 초기화와
실제 수명·안전 경계의 초기화를 구분한다. 패드 입력 취소와 해제·중립 대기는 두 경우 모두 유지한다.

| 경계 | 진행 중 터치·마우스·검색 처리 |
| --- | --- |
| 모드 변경·포인터 사용 전환 | 같은 문맥의 새 누름→해제와 검색 편집을 보존할 수 있음 |
| 게임 초점 변화·문맥 변경·창 닫기 | 진행 중 확인·포인터 입력과 검색 초점 폐기 |
| XInput 차단 경로 준비 상태 변화·소유자 연결 변화 | 진행 중 입력 폐기 후 기존 해제·중립 규칙 적용 |
| 대상 소멸·교체·선택 변경·게시 실패 | 기존 대상 검증에 따라 예약 입력 무효화 |

이 보존은 이전 패드의 실행 권한을 남기는 기능이 아니다. 포인터를 누를 때 기존 실행 권한을 먼저 취소하고,
필요하면 그 포인터 입력에 속한 새 예약 티켓을 만든다. 진행 중 포인터나 검색이 없으면 모드 변화 시 기존 초점을 취소한다.
터치로 모드가 바뀌었다는 이유만으로 누름의 원래 문맥·안정적인 컨트롤 ID·예약 대상을 잃지 않도록 한다.
위의 안전 경계는 입력 보존을 우회해 통과할 수 없다.

물리 키보드 탐색은 별도의 입력 활동 경로를 사용한다. 키 명령은 `OnGUI`에서 즉시 처리하므로 다음 `Update`는
누른 패드 입력과 전환을 소비하되 방금 키보드로 정한 초점을 다시 지우지 않는다. 같은 시점의 문맥·초점·연결 등
안전 경계는 여전히 우선한다. 키보드 예약 버튼 진입·다음 새 Enter/Space 예약과 홀드 차단을 함께 확인한다.
같은 프레임에 마우스가 움직였더라도 새 키 명령의 초점을 지우지 않는다. 명시적인 새 키 명령이 진행 중 클릭을 넘겨받으면
그 클릭의 ID·예약 티켓을 취소해 나중 터치·마우스 해제가 별도 동작을 실행하지 않게 한다.

## 버튼·검색·드래그의 입력 검증

Unity가 터치를 유효 마우스 이벤트로 변환하거나 `GUILayout.Button`이 이벤트를 소비할 수 있으므로,
버튼을 그리기 전 `rawType`과 유효 `type`의 터치/마우스 누름·해제를 함께 확인한다.
실제로 GUI 버튼이 눌렸다는 결과가 있어야 작동하며, 좌표에 손가락이 닿았다는 이유만으로 실행하지 않는다.
활성 버튼 안에서 누른 시작 ID·문맥과 해제 시점의 ID·문맥이 같아야 동작한다. 예약은 기존 티켓 검증도 필요하다.

- 터치·마우스의 누름, 이동·드래그, 정지와 휠을 포인터 활동으로 알린다.
- 검색 편집은 모드 변화로 중간에 닫히지 않게 보존하되 문맥·초점 등의 안전 경계에서는 취소한다.
- `TouchLeave`는 누르기 시작한 ID와 진행 중 확인을 취소해 나중 해제를 다른 항목에 사용하지 않는다.
- 탭·도구·닫기·예약 등의 상태 변경은 `GUI.Window` 그리기가 끝난 뒤 적용해 그리던 레이아웃을 중간에 바꾸지 않는다.
- 예약 버튼·대상·최신 조회/게시 상태와 별도 새 입력 계약은 [조작 초점 기록](ISSUE-4-ACTION-FOCUS.md)을 유지한다.

로그를 닫은 뒤의 게임 액션 해제 판단은 `Input.anyKey`뿐 아니라 `Input.touchCount == 0`도 기다린다.
손가락을 누른 채 닫은 입력이 게임의 다음 작동으로 전달되지 않도록 기존 콜백 차단 대기를 유지한다.
플러그인만 비활성화된 경우에도 게임 액션·XInput의 로그 소유권을 해제하고 중립 대기를 유지한다. 재활성화를 위해 기존 네이티브 연결을 폐기하지 않는다.
게임 액션 콜백 밖의 직접 상태 폴링과 실제 OS 이벤트 전달까지 자동으로 검증한 것은 아니다.

## 구현 범위와 이전 후보

네이티브 터치 이벤트를 직접 주입하거나 `simulateMouseWithTouches`를 전역으로 강제하지 않는다.
OS 터치→Unity 이벤트 변환과 실제 GUI·터치스크린 동작은 Windows 기기에서 확인해야 한다.
모든 터치 기기·드라이버·Steam Input 구성에서 동작한다고 보장하지 않는다.
앞선 [첫 표시·화면 비율](ISSUE-4-VIEWPORT-DEFAULTS.md), [탭 배치](ISSUE-4-TAB-LAYOUT.md),
[상세 조작 초점](ISSUE-4-ACTION-FOCUS.md) 수정도 작업 트리에 포함하며 다른 세션의 변경을 보존한다.
이전 후보의 해시와 검사 기록은 당시 결과로 보존하고 이번 후보의 실제 게임 확인 근거로 대체하지 않는다.
