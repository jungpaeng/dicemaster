# Release 작성 가이드

[사용자 README](../README.md) · [변경 이력](../CHANGELOG.md) · [빌드·게시 절차와 이력](RELEASING.md)

DiceMaster의 GitHub Release를 읽는 사람이 이번 버전의 변화, 설치 방법, 사용할 때의 제한을 판단할 수 있도록 작성한다. 정식판·시험판과 기존 Release의 본문 정리에 공통으로 적용한다. 이 문서는 설명을 쓰는 방법이며 빌드·패키지 검증은 [SOURCE-BUILD.md](SOURCE-BUILD.md)와 해당 버전의 배포 기록을 따른다.

## 문서별 역할

| 위치 | 담을 내용 |
| --- | --- |
| README | 현재 정식 버전의 소개·설치·조작·설정·문제 해결. 시험판은 차이를 별도 안내 |
| GitHub Release | 해당 버전의 사용자 변화, 설치·복구, 호환성·설정 변화, 검증 상태, 파일 확인 |
| CHANGELOG | 버전별 중요한 추가·변경·수정·제거. 여러 개발 커밋을 최종 사용자 변화로 묶음 |
| 버전별 `docs/*RELEASE.md`·구현/검증 문서 | 상세 지원 경계, 검사별 수치·방법, 확인 근거, Windows 검증표와 게시 기록 |
| 로컬 `artifacts/` | 재빌드·패키지·다운로드 검증 영수증과 원문 백업. Git에서 제외되므로 공개 근거 링크로 사용하지 않음 |

README에 매번 alpha와 로컬 후보 설명을 덧붙이지 않는다. 현재 안내를 갱신하고 이전 안내는 변경 이력·버전별 문서·Git 이력으로 보존한다. 절차 문서에서도 현재 규칙과 과거 게시 기록을 구분한다.

## 제목과 첫 문단

제목은 **`DiceMaster vX.Y.Z[-alpha.N] — 사용자에게 달라진 점`** 형식으로 쓴다. 예를 들어 `DiceMaster v1.0.5-alpha.9 — 목록 예약 표시·예약 해제`처럼 실제 변화를 적는다. 내부 PRD 번호·검사 수·커밋 SHA는 제목에 넣지 않는다. 안정성 표현은 실제 확인 근거에 맞춰 쓴다.

첫 문단은 무엇이 바뀌었고 누구에게 필요한지 한두 문장으로 설명한다. 이어서 **이 버전의 설치 ZIP**과 **최신 정식 버전** 링크를 둔다. 오래된 Release를 직접 방문해도 현재 설치 경로를 찾을 수 있어야 한다.

정식 버전은 직전 정식 버전 이후의 최종 변화를 모은다. 시험판은 직전 비교 가능한 시험판·정식판을 기준으로 차이를 설명한다. alpha 개발 순서를 그대로 복사하거나 최신 기능을 과거 버전에 소급하지 않는다. 예를 들어 alpha.6의 300ms 열기 제한, alpha.7의 제한 제거, alpha.8의 예약 설정, alpha.9의 예약·해제를 구분한다.

## 본문 순서와 포함 기준

1. **변경 사항:** 사용자가 볼 수 있는 동작을 묶어 설명한다. 원인이 유용하면 “선택 행이 화면 밖으로 벗어나던 문제를 수정해 포커스를 따라 스크롤합니다”처럼 이전 문제와 결과를 연결한다.
2. **설치·업데이트와 복구:** 모드 베이스 요구사항, Assets의 설치 ZIP, 최초 설치와 기존 cfg 보존 업데이트, 백업·복원 방법을 적는다.
3. **검증·알려진 제한:** 확인한 것과 남은 것을 구분하고, 지원 환경·입력·기능 제한과 대안을 적는다.
4. **파일 확인·상세 문서:** 파일별 SHA-256, 소스 커밋과 상세 기록·Windows 검증표 링크를 둔다. 길면 `<details>`로 접어도 된다.

버전에 따라 주요 조작표나 별도의 이행 안내를 추가한다. 잘못 설치하면 실행이 안 되거나 기존 입력·설정이 달라지는 변화는 다운로드 근처에 먼저 알린다. 분량의 고정 상한은 두지 않고 설치·사용 결정을 돕는 정보인지로 판단한다.

### 본문에 직접 남길 정보

- 새 기능·수정·제거와 정확한 적용 버전. 예약과 즉시 실행, 선택과 확정, 일회 우회와 영구 상태 변경을 구분한다.
- 기존 설정 보존 방법과 변경된 기본값·설정 키. 게임 재시작이 필요한 변경과 도구에서 바로 적용하는 변경을 구분한다.
- 버튼 조합·입력 소유권이 사용자 조작에 주는 영향. 예를 들어 패드 열기 옵션이 단독 L3/R3도 차단한다면 조건과 끄는 방법을 함께 적는다.
- 알려진 회귀, 지원하지 않는 환경·경로, 오류 시 복구 방법. 대안이 있으면 해당 버전이나 설정을 명시한다.
- 이번 DLL의 자동 검사·실제 Windows 확인 상태. 정식 배포 채널과 기능·이슈 완료를 같은 의미로 쓰지 않는다.

### 상세 기록으로 연결할 정보

개별 검사 프로그램의 단언 수, 전체 빌드 입력 목록, API·객체 검증의 세부 구조, Release/asset ID, 게시 옵션과 영수증은 상세 문서에 둔다. 변경의 핵심이 빌드 체계라면 그 의미는 본문에 설명하되 전체 작업 일지는 옮기지 않는다. 커밋·PR 비교 링크는 보조 근거로 사용하고 사용자 설명을 대신하지 않는다.

## 설치·해시·링크 작성

기본 설치 자산은 `DiceMaster-vX.Y.Z[-alpha.N].zip`이며 내부 경로는 다음과 같다.

```text
config/DiceMaster.cfg
plugins/DiceMaster/DiceMaster.dll
```

게임을 종료하고 DLL·cfg를 백업한 뒤, 업데이트는 DLL만 교체해 cfg를 보존하도록 안내한다. 최초 설치에는 두 파일을 넣는다. 예외가 있는 버전은 예외와 이유를 설명한다. GitHub 자동 `Source code` 압축 파일과 설치 ZIP을 구분하고 게임 소스·게임 DLL·다른 모드를 포함하는 것으로 오해하게 쓰지 않는다.

복구는 게임 종료 후 백업 DLL과 필요한 cfg를 복원하는 절차다. 이전 버전에서 제공하지 않는 기능이나 알려진 회귀를 알린다. DLL 복원은 이미 진행·저장한 게임 상태를 되돌리는 기능이 아니다.

해시는 실제 게시 파일·검증 기록에서 가져온다. ZIP과 DLL의 SHA-256을 제공하고 필요하면 cfg도 포함한다. 파일명·크기·해시가 서로 다른 후보에서 섞이지 않게 대조한다. 로컬 경로와 `artifacts/` 링크는 공개 Release에서 열리지 않으므로 공개된 버전별 문서로 연결한다.

GitHub Release 본문의 문서·이미지 링크는 **검증한 공개 절대 URL**을 사용한다. 당시 동작·검사 근거는 고정 커밋 URL을 우선한다. 게시 후 작성한 문서는 그 문서를 포함한 별도 커밋으로 연결하고, 빌드 소스 커밋과 문서 커밋을 혼동하지 않는다. 설치 ZIP 링크는 해당 Release의 실제 자산 이름을 사용한다.

## 검증 상태를 표현하는 방법

| 근거 | 가능한 표현 | 확대해서 쓰면 안 되는 내용 |
| --- | --- | --- |
| 로컬 자동 검사 | “관리 코드·모의 게임 경계의 자동 검사를 통과했습니다” | 실제 Windows 화면·물리 패드·성능까지 확인했다는 표현 |
| 고정 커밋 재빌드·공개 파일 대조 | “해당 커밋 빌드와 공개 ZIP의 바이트·해시를 확인했습니다” | 게임 동작·입력 호환성이 보장된다는 표현 |
| 사용자의 실제 게임 확인 | 확인한 버전·일시·항목과 알려진 환경 범위를 기록 | 제공되지 않은 게임·로더 버전·장치·항목별 결과 추정 |
| 같은 파일의 정식 승격 | 기존 검사 출처와 입력·파일 동일성, 재실행 여부를 기록 | 이전 검사 결과를 이번 새 검사 실행으로 표현 |

최신 사용자 확인이 도착하면 버전별 문서에 날짜와 대상 버전을 덧붙이고 현재 README의 상태를 갱신한다. 과거 게시 당시의 “확인 대기” 기록은 당시 시점임을 표시해 보존한다. 새 DLL에 이전 버전의 Windows 확인을 자동으로 승계하지 않는다. 같은 파일의 검증 근거를 재사용할 때도 실제 동일성을 확인하고 출처와 확인 범위를 명시한다.

미확인은 한 곳에서 명확하게 알리고 상세 검증표로 연결한다. 같은 면책 문구를 문단마다 반복할 필요는 없지만 입력 차단·예약 의미·알려진 오류처럼 사용 판단에 필요한 제한은 접힌 상세 문서에만 숨기지 않는다. 시간·메모리 수치는 측정 환경과 방법을 함께 적고 다른 환경의 실게임 성능으로 일반화하지 않는다.

## 게시·기존 본문 정리 시 확인

새 Release를 작성할 때는 대상 버전의 기능·설정·자산과 문서가 일치하는지 확인하고, 게시 후 공개 페이지의 제목·본문·링크와 파일 식별값을 확인한다. 시험판 게시가 기존 Latest 정식을 바꾸지 않는지도 확인한다. 검증 횟수나 검사 목록은 실제 결과에서 읽고 이전 문서의 고정 개수를 복사하지 않는다.

이미 게시한 Release를 정리할 때는 원문과 메타데이터를 먼저 보관하고 **제목·본문만** 편집한다. 태그·커밋·배포 파일·게시일·정식/시험판 구분·Latest를 보존하고 저장 결과를 다시 읽어 대조한다. 동시 편집이 있다면 백업과 현재 원문을 비교해 다른 변경을 덮어쓰지 않는다. 본문 수정에 따른 수정 시각 갱신과 원래 게시일은 구분한다.

문서 작성·기존 본문 정리를 새 태그 생성·코드 push·자산 교체 지시로 확대하지 않는다. 새 게시·정식 승격은 해당 작업의 사용자 지시 범위에서 진행한다. 이미 받은 지시를 같은 행동에 대해 반복 확인하는 절차를 추가하지 않는다.

마지막으로 제목·첫 문단, 버전별 기능 차이, cfg 보존 설치·복구, 검증 상태, ZIP/DLL 해시와 공개 링크를 훑어본다. 사용자에게 필요한 경고가 본문에서 보이는지와 상세 접기·표·목록이 정상적으로 읽히는지도 확인한다.

## 이 구성을 선택한 근거
