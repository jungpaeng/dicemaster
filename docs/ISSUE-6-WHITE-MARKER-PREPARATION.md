# PRD #6 — 흰 마커 준비 대기 개선

2026-10-23. 기준은 `main`의 `48ac7f11bb73e75f609cb24ffb12c51db93c62d3`(게시된 alpha.41의 소스 동작)이다. 원래 작업 폴더의 main에서 진행하며 별도 브랜치·worktree를 만들지 않는다. 이 문서는 **alpha.41 이후 alpha.42 후보 변경**이다. [소스 고정 재빌드·게시 기록](ISSUE-6-ALPHA42-RELEASE.md)에서 릴리스 상태를 별도로 확인한다. 실제 Windows 확인과 #6 전체 완료는 대기다.

## 적용한 세 단계

1. **파괴된 장소 등록 정리.** 게임의 장면 교체로 파괴된 Unity 객체와 수명이 끝난 weak 참조만 등록/스냅샷 초기화 시 정리한다. 숨김·비활성 상태의 살아 있는 장소는 보존한다. 파괴된 선택/상세 참조와 발행 문맥도 무효화한다. 새로운 전역 Unity 검색이나 게임 객체 생성은 하지 않는다. 기존 `ClearSnapshots`가 원천 데이터만 버리고 등록 목록은 남기던 누적을 막는다.
2. **실패 재시도 대기는 순서 양보.** 배경 준비가 원문/풀 읽기와 경로 작업을 전혀 소비하지 않은 경우 다음 보이는 장소를 같은 제한된 순회에서 확인한다. 최초 실패 읽기는 슬롯을 사용하며 여전히 실패 후 5초에 재시도한다. 정상 장소의 첫 안내를 읽기 실패 장소 수만큼 추가 대기시키지 않는다. 스크립트가 없는 장소는 준비 시도를 하지 않는다.
3. **첫 안내 이후 선택 장소와 배경 작업의 공정성.** 현재 입력이 같은 유효 경로 근거를 이미 갖춘 선택 장소는 무관한 후속 스크립트 준비를 잠시 양보한다. 마커 조회가 다른 갱신 시점이라 슬롯을 쓰지 않았다면 같은 예약 범위 끝에서 원래 마감시간으로 선택 장소 작업을 이어 간다. 최대 네 번 양보하면 선택 장소가 우선권을 회복하며, 마감시간 소진도 양보 횟수에 포함해 선택 장소의 나머지 경로·1회성 자료 준비가 영구히 굶지 않도록 한다. 최초 근거가 없거나 근거의 현재 입력이 바뀌면 기존 선택 장소 우선을 적용한다. 명시적인 상세 로그 조회는 양보하지 않는다.

한 화면 예약 범위는 기존 원문 읽기 최대 1회·풀 읽기 최대 1회·8192 경로 작업·협력식 약 5ms를 공유한다. 끝에서 이어 가는 작업에 새 예산을 주지 않는다. 정상 0.25초/실패 5초·숨김/OFF 중단·현재 조건 재검증·메뉴 완결/해금/완료/반복 활동 판정·입력 소유권은 유지한다. 게임의 조건 함수·판정·RNG·세이브·아이템·능력치를 쓰지 않는다. 주사위 자동 이야기 안내를 복원하지 않는다.

## 단계별 비교와 한계

모두 macOS .NET 8 Release에서 운영 provider와 관리 경계로 측정했다. 조회 번호와 가상 프레임은 Windows 지연 초나 실제 FPS가 아니다. 처음부터 마커가 있는 대기 임무/검증 1회성은 깊은 이야기 준비보다 먼저 처리한다.

준비 순서 개선은 전체 분석량을 줄인다는 뜻이 아니다. 모든 조건을 안 읽고 첫 대사에서 끊거나, 한 번 참인 마커를 영구 고정하지 않는다. 이미 확인한 경로의 관련 입력을 매번 검증하며 불충족·완료 시 제거하고 새 해금은 다시 찾는다.

빈 스크립트의 준비 후보까지 모두 재시도하는 중간안에서는 정상 조회 할당량이 증가했다. 최종에서는 빈 스크립트를 준비 목록에서 제외했다. 그 중간안의 `comparison/final-1-ready`를 최종 개선 수치로 인용하지 않는다. 최종 반복 비교의 수치와 실제 원문·갱신 시점 비교는 아래 영수증에 기록한다. 건강한 정상 조회의 일반적인 CPU/FPS 향상을 주장하지 않는다.

## 최종 반복 측정

같은 probe를 기준과 변경에 각각 세 번 연결했다. 채택한 기준은 `comparison/baseline-1-ready`, `baseline-2`, `baseline-3`, 변경은 `final-5`, `final-6`, `final-7`이다. 집계는 `artifacts/issue-6/white-marker-preparation-stages/summary.json`에 남긴다.

- 기존 54개 마커 비교의 최종 표시 SHA-256·첫/전체 마커 조회 번호·정상 조회 할당량이 모두 기준과 같다. 정상 추가 원문 읽기 0회, 준비 중 한 조회 최대 원문 읽기 1회다. 추가 순서 비교 27건도 최종 표시 SHA-256이 같다.
- 100회 장면 재생성 뒤 정상 marker provider의 중앙 p50은 0.04946 → 0.03538ms, p95는 0.05688 → 0.04325ms, 할당은 15,924 → 15,472 B/조회였다. 파괴 객체 누적이라는 조건에 대한 managed 측정이며 일반 게임 FPS 수치가 아니다.
- 정상 상태의 다른 마커 사례는 비용이 비슷하고 시간 변동도 남았다. 이번 변경의 주효과는 불필요한 준비 대기와 장면 누적 제거다.

실제 게임 원문·설치 정의와 합성 기본 상태를 사용한 세 번의 비교에서 남제자방을 계속 포커스하면 여제자방의 첫 흰 마커가 **38 → 16번째**, 연단방은 **47 → 27번째**, 강경단은 **55 → 36번째 조회**였다. 남제자방 자신의 첫 마커는 양쪽 모두 5번째였다. 연단방 포커스에서는 여제자방 **28 → 17번째**, 남제자방 **30 → 19번째**, 강경단 **43 → 34번째**, 연단방 자신의 첫 마커는 양쪽 모두 6번째였다. 같은 250회 동안 원문 읽기는 각 경우 168/158회로 기준과 같고 확인된 마커의 중간 누락은 없었다. 무포커스에서는 첫 세 장소의 중앙값 7/9/19회가 같았다. 이 비교는 최종 마커 하나에 필요한 준비 순서이며 사용자 저장의 실제 가능 여부를 재현한 검사는 아니다.

두 독립 RefreshEngine의 가상 60Hz 비교에서는 17번째 프레임에 남제자방을 포커스한 경우 다른 장소 첫 표시가 여제자방 **528–560 → 208**, 연단방 **672–704 → 390**, 강경단 **800–832 → 512프레임**으로 줄었다. 반면 선택 장소 자신의 첫 표시가 어떤 cold 실행에서는 48 → 64프레임으로 늦었고, 무포커스의 연단방도 270 → 270–285프레임으로 변동했다. 초기 JIT·협력식 마감시간·서로 다른 갱신 위상의 영향이 남으므로 모든 첫 표시가 빨라졌다고 주장하지 않는다. 고정 동기 조회와 장기 지연 사례의 개선을 확인해 채택하고, Windows 첫 프레임 및 포커스 전환 지연은 별도 확인 대상으로 남긴다.

## 재현과 원본 결과

```sh
python3 tools/benchmark-guidance-markers.py --baseline 48ac7f1 --modes scheduling unselected selected deep --output artifacts/issue-6/white-marker-preparation-stages/recheck/baseline
python3 tools/benchmark-guidance-markers.py --modes scheduling unselected selected deep --output artifacts/issue-6/white-marker-preparation-stages/recheck/current
```

.NET 8 SDK를 PATH에 두거나 `--dotnet`으로 지정한다. 필요하면 기존 NuGet 캐시를 `NUGET_PACKAGES`에 지정한다. 이전 측정을 덮어쓰지 않는다. `scheduling`은 실패 대기·선택 장소의 많은 후속 경로·100회 장면 재생성을 포함한다. 기존 세 모드는 8/32/64개 장소·무관 조건 0/4096개·포커스/무포커스/3단계 경로를 비교한다. 기준과 변경 모두 같은 probe와 provider 호출 순서를 사용한다.

- `artifacts/issue-6/white-marker-preparation-stages/baseline/`: 변경 전 분석의 실행 파일·소스와 원본 측정. `actual/no-focus.json`은 원천 배열을 매번 새로 만들던 잘못된 초기 probe이므로 채택하지 않는다. 이름이 `none-1.json` 등인 수정 후 측정만 사용한다.
- `01-lifecycle/`, `02-retry/`, `03-fairness/`: 각 단계의 독립 비교. 기존 파일을 덮어쓰지 않는다.
- `comparison/`: 같은 probe를 Git 기준과 현재 소스에 연결한 반복 비교. 최종 채택 목록은 `summary.json`에서 명시한다.
- `final-native-inputs-v2/`: 실제 2,199개 Lua/설치 정의를 읽고 게임 기본 플래그와 1년 4월의 합성 현재 상태를 사용한 비교. 파일 준비는 타이밍 전에 끝낸다. 여기서는 흰 안내 순서만 분리하기 위해 1회성 설정을 끈다. 사용자 세이브·실제 Unity I/O·게임 Lua 실행을 포함하지 않는다.

실제 원문 비교에서 지도 11곳과 남제자방/연단방 포커스를 각각 확인한다. 별도 두 RefreshEngine을 60Hz 가상 프레임으로 구동하고 1/17/20번째 프레임에 포커스를 바꾸는 검사도 포함한다. 갱신 위상과 약 5ms 마감시간에 따라 결과가 변하므로 특정 조회 횟수를 고정된 사용자 대기시간으로 바꾸지 않는다.

## 자동 검사와 남은 Windows 확인

회귀 검사는 파괴/숨김/재활성화·오래된 쿼리 거부, 실패 재시도 간격, 전체 예약 범위의 읽기/작업 상한, 다수 동료와 선택 장소의 완료, 마커 조회가 없는 프레임의 슬롯 회수, 만료된 배경 마감시간에서의 선택 우선 복구, 숨김/초기화 후 늦은 작업 취소를 포함한다. 기존 완료·해금·우소매 false AND·RNG·반복 활동·입력·정의 파일 검증도 유지한다.

실제 Windows에서는 새 게임 및 완전 재시작 후 저장 불러오기에서 남제자방·연단방·여제자방·강경단의 첫 스피너/마커를 비교한다. 무포커스/같은 장소 계속 포커스/빠른 포커스 변경을 구분한다. 장면을 여러 번 오간 뒤 첫 표시와 GC가 누적 악화되지 않는지, 완료/잠금 후 제거와 재해금, 다른 창/로그/OFF 복귀, 금색 기회 마커와 Xbox/XInput·키보드·마우스·터치를 확인한다. 프레임 p95·GC 정지와 전체 준비 시간을 별도로 측정한다. 기존 지도 성능 상세는 선택 장소 provider 표본이며 배경 및 예약 범위 끝의 작업을 포함한 전체 프레임 계측이 아니다.

설치 정의 최초 해시/연결, 큰 원문의 메인 스레드 Resources 읽기, 루트 메뉴 완결과 안전한 조건 판독 비용은 이번 변경으로 사라지지 않는다. 이 비용이 실제 Windows에서 지배적이면 별도의 측정이 필요하다.

## 최종 로컬 후보 영수증

고정 참조 16개와 소스/검사/빌드 입력 315개를 검증한 새 DLL에서 전체 21개 검사 프로그램을 통과했다. 실제 설치 파일과 원문을 제공한 MapGuideRouteIntegrationTests 4,557개, InformationRuntimeTests 7,262개, ChoiceStoryTests 7,822개를 포함한다. 초기에 얕은 MapInformationTests fixture에 새 ReadStamp 메서드가 없어 빌드가 멈췄으며, 캐시 적중을 주장하지 않는 보수적 shim을 추가한 뒤 전체를 다시 검사했다. 실제 조건 판독/ReadStamp 회귀는 운영 소스를 연결한 별도 route integration에서 계속 검증한다.

사용자 복제본의 DLL을 참조해 모드와 API 검사기/fixture를 새로 빌드하고 4,265개 managed behavior / 1,288개 metadata contract를 통과했다. 두 참조 경로에서 모드 DLL 바이트가 같으며 소스 및 참조 파일의 검사 전후 해시가 같다. Unity/Harmony·게임 Lua·Windows 실행 결과가 아니다. 설치 ZIP 두 경로의 CRC·cfg/DLL 바이트도 새 후보와 대조했다.

- DLL: 1,105,408 B · SHA-256 `9cc25e380e22af4936e860089dab8de615a32b80bba2bc3ca1ebee97f5116511`
- ZIP: 436,859 B · SHA-256 `71cf293d885c506f9bbc401ebd91a898ac41f55a940963ab5f0d5079327d77e9`
